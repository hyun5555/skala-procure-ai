# ADR-0001: 기존 실행 구조를 유지하며 개인 AI 조달 개발을 시작한다

## Status

Accepted — 2026-10-06. 사용자 요청에 따라 개인 개발 기반으로 전환한다. 신규 API·LLM 호출·주문 마이그레이션은 이 ADR로 구현 완료를 의미하지 않는다.

## Context

프로젝트는 팀 실습용 Vue·Spring·FastAPI 서비스와 MariaDB·Kafka로 구성되어 있다. 개인 개발의 첫 목표는 자연어 구매 조건 확인, 규칙 기반 공급업체 비교, 근거 설명이다. 기존 팀 작업은 이력으로 남겨야 한다.

교육 이미지로 제공된 인증·게이트웨이는 앱 소스가 없고, 경로·redirect URI·역할 계약이 기존 서비스를 묶고 있다. 발주는 사용자·품목 쌍에 유일 제약이 있고 결제 이벤트도 같은 쌍을 사용한다. 조건 점수의 문서·코드 기준 또한 다르다.

## Options

| 선택 | 장점 | 대가 |
| --- | --- | --- |
| 기존 서비스에서 추천 범위만 확장 | 기존 거래 흐름을 보존하며 작은 변경 검증 가능 | 다중 서비스 기동·배포 부담과 교육 이미지 의존이 남음 |
| 단일 백엔드로 통합 | 개인 운영의 구조가 단순해짐 | 인증·데이터·이벤트 이관으로 첫 사용자 기능이 지연됨 |

## Decision

기존 실행 구조와 `/api/...` 계약을 유지하면서 recommend-service 안에서 확장한다. 팀 운영 지침은 기록으로 보존하고 개인 작업 지침은 실제 변경·검증 책임을 중심으로 정리한다.

1. 규칙 매칭은 필수조건 판정 후 점수화한다. 가격·인증·규격 판정의 근거는 카탈로그와 서버 계산이며 LLM이 확정하지 않는다.
2. LLM은 구매 요청의 조건 초안과 검증된 결과 설명을 담당한다. 조건 확인은 사용자 화면에서 수행하며 자동 발주·결제는 포함하지 않는다.
3. 조건 점수와 QCD를 별도 표시한다. 점수 축·가중치와 평가 표시는 문서·코드 차이를 기록한 뒤 별도 결정한다.
4. 신규 API는 `/api/recommend/parse`, `/api/recommend/match`로 제안한다. 기존 GET은 호환 유지하며, 제공자·모델은 아직 선택하지 않는다.
5. 인증·게이트웨이 교체는 독립 실행 또는 배포 단계의 별도 ADR로 진행한다. 기존 역할·소유권을 보존하고 직접 서비스 접근·헤더 위조까지 검증한다.
6. 반복 발주·견적 협의는 주문 식별자, 결제 이벤트, 상태, 스키마 마이그레이션 이후 진행한다.

벡터 DB, 새 서비스, 언어 전환, 전면 rename은 초기 범위에 포함하지 않는다.

## Consequences

첫 기능을 작은 변경으로 개발하고, LLM이 실패해도 수동 입력과 규칙 결과를 유지할 수 있다. 기존 동작과 비교할 기준도 남는다.

교육 템플릿 용어와 여러 서비스 운영 비용은 당분간 유지된다. 인증·게이트웨이 독립 실행과 주문 구조 변경에는 후속 작업이 필요하며, 추천 API 추가만으로 공개 배포 준비가 끝나지 않는다.
