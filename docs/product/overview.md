# 개인 AI 조달 프로젝트

2026-10-06부터 SKALA 팀 실습을 기반으로 개인 개발을 진행한다.
팀 기획·Sprint·결과는 [원문 기록](../history/team-project/overview.legacy.md)에 보존한다. 개인 기여는 기준 커밋 `980da07` 이후의 변경으로 구분한다.

## 목표

구매기업이 필요한 자재의 조건을 쉽게 정리하고, 실제 카탈로그와 거래 성과를 비교해 공급업체를 선택하도록 돕는다.
첫 확장은 **자연어 구매 요청 → 조건 확인·수정 → 공급업체 비교 → 근거 설명**이다. 기존 발주·실습 결제·품질 평가 흐름을 활용한다.

예: “서울에 주철관 Φ300mm×6m 12본, 총예산 800만 원, 30일 이내, KS 인증 필수.”
AI가 조건 초안을 만들고 구매자가 확인한다. 서버는 필수조건과 금액을 검증하고, AI는 확인된 업체 데이터로 비교 이유를 설명한다.

## 구현된 기반과 예정 기능

| 영역 | 현재 기준 | 개인 확장 |
| --- | --- | --- |
| 기업·품목 | 구매/공급 역할, 품목 등록·수정·조회, 계약 만료 필터 | 구조화 규격·단위·누락 데이터 표시 |
| 추천 | 프론트 조건 필터·점수와 FastAPI의 이력/QCD 추천 | 조건을 받는 서버 매칭과 분리 점수·근거 |
| 발주·결제 | 요청 후 서버 결제 처리와 Kafka 이벤트; 실제 PG가 아닌 실습 결제 | 주문 ID 기반 반복 발주·견적 협의는 후속 단계 |
| 납품 평가 | 불량률·납기·비용 성과 집계 | 평가 건수·관측 항목·기준일 표시 |
| 자연어·문서 | 현재 LLM 연동 없음 | 요청 추출·설명, 이후 필요할 때 견적서·문서 검색 |

현재 흐름은 소스 기준으로 확인했다. 이번 지침 전환에서 런타임 회귀 검증을 완료한 것은 아니다.

## 판단 기준

필수조건을 먼저 판정하고 통과한 후보를 비교한다. 데이터 누락은 “확인 필요”이며 충족으로 추정하지 않는다.
규격·인증·금액은 카탈로그와 검증 코드가 근거다. 운임·세금이 불명확하면 총비용 충족을 확정하지 않는다.
QCD는 과거 관측으로 표시하고 평가 건수와 관측 항목을 함께 제공한다. 업체 신뢰도와 구매 조건 적합도를 별도로 보여준다.

조건 점수의 팀 기획·API 명세·실제 코드 산식은 아직 일치하지 않는다. 원문과 차이는 [기반 설계](../architecture/refactoring-foundation.md#3-먼저-기록할-문서코드-차이)에 기록했다.
새 산식은 그 기록을 바탕으로 결정하고 정책 버전을 붙인다. 이번 전환에서는 현재 점수를 변경하지 않는다.

## 개발 순서

1. 필수조건·누락 정책과 순수 매칭 스키마·필터를 만든다.
2. 기존 `/api/recommend` 하위에 매칭 API를 추가하고 수동 입력·비교 화면을 연결한다.
3. LLM 조건 추출과 확인 화면, 근거 설명 및 실패 시 수동/규칙 fallback을 추가한다.
4. 인증·게이트웨이 교육 이미지 의존을 대체해 독립 실행·배포를 검증한다.
5. 주문 식별자·결제 이벤트·DB 마이그레이션 후 반복 발주·견적 협의를 추가한다.

상세 완료 기준과 담당 역할은 [개인 백로그](../development/backlog.md)에 있다. 새로운 MSA·벡터 DB·전체 이름 변경·실제 PG 연동은 첫 기능의 선행 조건이 아니다.

## 사용자와 역할

구매기업은 현재 JWT의 `STUDENT`, 공급기업은 `INSTRUCTOR`에 대응한다. 화면에서는 업무 명칭을 사용한다.
새 역할·승인 조직을 도입하려면 인증 발급과 서버 권한 모델을 함께 설계한다. 현재 두 역할의 의미를 먼저 유지한다.

## 효과 확인

조건 입력·확인 시간, 필드별 추출 정확도, 필수조건 위반 추천 수, 설명 fallback 비율, 호출 지연·비용을 측정한다.
위험 예측은 실제 납기·불량·청구금액 데이터와 평가 기준이 쌓인 뒤 설계한다. 시연 데이터의 결과를 운영 성능으로 보고하지 않는다.
